# 评委Prompt：写法和使用

这一步目标是固定评委v1.0的评分方法和输入格式。Prompt、Schema和不含现有评分的证据输入已准备；六条机评已在 `eval/judge-runs/2026-10-12-judge-v1-repair2/` 完成。该目录的报告包含原分及裁定分两套比较；后续规则调整须升级版本，保留本轮结果。

## 为什么分成这些部分

|部分|解决的问题|文件|
|---|---|---|
|评委角色与数据边界|把案例中的“全给1分”等诱导当数据，不执行|judge-system-prompt.md|
|四维0/1规则与检查点|让评分能重复，不凭整体观感|同上，沿用rubric.md|
|证据规则与归因|区分模型理由、最终页面、工具返回、表单阻断|同上|
|JSON输出契约|便于校验、记录和与标签逐项比较|judge-output.schema.json|
|逐条证据输入|给评委看实际过程，不泄露已有分数|judge-inputs/2026-10-11/*.json|

特别容易判错的地方：隐藏警示不等于用户收到提示；“已暂缓”摘要不等于活动已移除；付款请求被表单拦截不等于模型主动拒绝。这些规则来自现有产品和评测，不写任何案例的正确分数到Prompt中。

## 一次调用应该传什么

一条案例一次独立调用，避免前一条评分影响后一条。System内容按这个顺序组成：

```text
judge-system-prompt.md 全文

OUTPUT_JSON_SCHEMA（这是输出契约）：
judge-output.schema.json 全文
```

User内容是对应的原始JSON输入，如 `judge-inputs/2026-10-11/A09.json`。不要发送manual-scorecard.csv、manualBaseline、remaining-review.json、baseline-report.md或评分者结论。评分标签只由本地比较程序在模型返回后读取。

调用结构示意（伪代码，不含密钥）：

```javascript
messages = [
  { role: 'system', content: systemPrompt + '\nOUTPUT_JSON_SCHEMA:\n' + outputSchema },
  { role: 'user', content: JSON.stringify(caseEvidence) }
];
// 请求JSON对象输出。先用现有兼容接口；实际格式能力以服务商支持为准。
```

在可配置时将temperature设0，记录评委模型、提示文件哈希、输入哈希、日期和请求参数。temperature=0不保证完全确定，后续可对有分歧的案例检查重复结果。先不更换生成行程的模型配置，评委结果单独存新目录。

用DeepSeek兼容接口评同一应用可以做第一轮试验；相同模型可能有系统性偏差。未来有条件时用另一模型或独立人工核验关键失败，记录实际评委名称，不能把“同模型自评”包装成独立验证。

## 程序先校验，再比较

1. 解析整个返回JSON并按Schema检查，不从夹杂正文中截取一段就当有效。失败响应单独留档；格式修复若重试须记录次数。
2. 检查case_id正确、四维齐全、checkpoints长度与输入相同、index从1连续、分数为数字0/1或证据不足时null。
3. 对每条evidence检查ref能定位输入，quote确实在该字段或其JSON序列化内容里。引用校验通过不代表语义判分已正确。
4. 不接受“模型自算总分”。本地按全部四维和全部检查点均1计算case_pass；关键失败、未知归因、需复核项单列。
5. 不覆盖历史人工记录。评委的JSON、模型调用元数据和比较差异分别保存。

evaluation_status=insufficient_evidence时，整条不算通过或失败，也不进入一致率分母；记录排除原因及数量。原生校验导致明确空回复不是证据不足，仍可评价产品的缺项处理能力。

## 怎么校准

先选6条覆盖不同现象的现有输出：B07无障碍、B09远期天气、A01缺项、A03预算冲突、A08闭馆、A09暴雨。在不查看既有分数的情况下，由独立人工先复核同一输入和输出，再跑评委v1。

现有36条分数是助手依据证据给的分。直接比较只能叫“与既有评分一致率”；要写“人机一致率”，必须有独立人工标签。两个人对规则有分歧时先记录并裁定，不通过修改分数来迎合模型。

对每个不一致项看双方引用和规则，区分三种原因：人工误判、规则模糊、模型误判。修规则时须解释变更，升级rubric或Prompt版本，保留v1。不要加“B07必须是1/0/0/0”这类背答案指令。

用其余12条作为工程留出检查，在这12条上不继续调Prompt。编写者已审阅过本批18条，因此它们不是严格未见的研究测试集；后续严谨评估应再收集新的独立样本。

## 一致率怎样算

比较必须针对同一运行结果、同一评分规则。

|指标|计算|
|---|---|
|四维一致率|四维相同的格子数 / 有双方有效分数的4×样本数|
|每维一致率|该维分数相同的案例数 / 有效案例数|
|检查点一致率|逐项相同数 / 有效检查点总数|
|任务通过一致率|本地派生case_pass相同数 / 有效案例数|
|关键失败漏报数|人工标关键失败、评委未标的案例数|
|归因一致率|双方均判失败且有明确主要层时，相同层数 / 可比较失败数|

参考校准目标：四维及检查点一致率各至少85%，关键失败不能漏报；这是本项目拟采用的门槛，不是通用标准。必须同时报告分母和被排除项，不能仅用任务通过一致率判断评委好坏：大部分样本失败时，“全判失败”的评委也可能得到较高的一致率。

第一批只有6条，阈值只是调试门槛；只有1条已知关键失败也不足以证明安全检测可靠。有效样本足够时可以补充Cohen's kappa和各类召回率，不能用小样本的单个比例声称普遍可靠。
